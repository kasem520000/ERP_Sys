## The honest repair this wave (the W-4 controller repair's own class, pre-existing, zero behavior change)

**`EosbService`'s DI shape**: the W-2-era constructor declared `@Inject` on
the audit param only — `posting` + `eos` relied on tsc's
`emitDecoratorMetadata` (correct in the production build), but the
vitest/esbuild transform emits NO `design:paramtypes`, so W-5's route-level
spec (booting the controller — and the service through it — via the real
Nest pipeline under that transform) resolved them `undefined` and the
true-up route 500'd. The repair: the explicit `@Inject()` tokens on every
param (the identity/hr house pattern) — mechanical, token = the same class,
zero production behavior change. The eosb.spec suite (which constructs the
service manually) never surfaced it — the same latent shape the W-4
controller repair documented.
