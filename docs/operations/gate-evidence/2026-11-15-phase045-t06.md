## What landed (T-06)

- **The rules** (HR-03): CRUD + activate/deactivate — the code unique
  per tenant, the tier/multiplier (1–5)/cap ((0…16]) bounds typed
  BEFORE any write (the 0082 CHECKs surfaced as the RULE error family),
  the cap clearable (an explicit null — its own statement, COALESCE
  cannot express "set to NULL").
- **THE TIER-MATCHING LAW:** a work date resolves to exactly ONE tier —
  HOLIDAY (the tenant-jurisdiction calendar — the attendance
  derivation's law) > WEEKEND (the date's ISO weekday in the tenant's
  `hr.overtime.weekend_days` setting — Monday=0…Sunday=6, the rotation
  pattern's index convention) > WEEKDAY (the complement). While the
  weekend setting is UNCONFIGURED the WEEKEND tier never auto-matches —
  NO fabricated default (the BR-055 discipline; inventing "Sat/Sun"
  would be wrong for Saudi and wrong for others — the jurisdiction
  regime is PHASE-046's). An AMBIGUITY (2+ ACTIVE rules on the tier)
  and an UNAVAILABILITY (none) are typed refusals — never a silent
  pick; the entry may also name its rule EXPLICITLY (the schema's law).
- **BR-084 (the pre-approval enforcement):** a pre-approval-required
  rule's PENDING entry carries `is_exception = true` (the exception
  board's feed — unapproved required time is NEVER silently fed); a
  rule WITHOUT the requirement records post-hoc worked time (PENDING is
  not an exception — it feeds; REJECTED never feeds); the APPROVE and
  REJECT decisions both clear the exception (a decided verdict is not
  an open exception) and stamp the approver + timestamp; a decided
  entry never re-decides (the typed 409).
- **THE PER-DAY CAP:** a rule's `max_hours_per_day` bounds the
  employee's SANCTIONABLE day-total under THAT rule (PENDING +
  APPROVED — REJECTED time never counts), enforced typed BEFORE any
  write; the 16h-per-entry bound is the DB's CHECK floor.
- **THE MULTIPLIER APPLICATION:** hours × multiplier computed in SQL
  NUMERIC math, cast `numeric(7,2)` (exact — the pay-relevant product
  never rides float; ADR-0009). Hours and multipliers cross the API as
  DECIMAL STRINGS.
- **The reads:** the entries list paginated (total + hasMore) with the
  employee + rule dims and the exact multiplied hours; the exception
  filter (`is_exception`) for the board.
- **The routes:** rules CRUD + activate/deactivate, the tier match
  (`GET overtime/tier?date=`), the weekend setting (GET/PUT), the
  entries (create / approve / reject / list) — every row
  `@RequirePermissions("hr.overtime")` + ROUTE_PERMISSIONS-registered
  (the §8 law). The audit trail: `hr.overtime_rule_*`,
  `hr.overtime_weekend_saved`, `hr.overtime_entry_created/approved/rejected`.
