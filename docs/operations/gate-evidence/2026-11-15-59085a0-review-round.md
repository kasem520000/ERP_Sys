## Item 2 — THE FAILURE PATH UNDER AN ABORTED TRANSACTION (the owner's contract question, answered and fixed)

### 2a. The defect, reproduced and pinned live

The owner's sequence: the trial-balance compute hit the 15 s
`statement_timeout` (pg 57014) — any pg query error ABORTS the ambient
`withTenant` UoW — and then the FAILED recording itself failed
"because the transaction was aborted". This round reproduced the exact
shape with a debug run (an exploding test contract executing
`SELECT 1/0` on the ambient tx): the pre-fix catch called
`store.failRun` (an UPDATE **on the aborted transaction**), which died
with **25P02 "current transaction is aborted"** — and that SECONDARY
error **replaced the original in the caller's output** (the drizzle
wrapper's message embeds the failing `UPDATE report_runs`, its
`cause` the 25P02), while the `withTenant` rollback erased the whole
attempt — nothing recorded, wrong error surfaced.

### 2b. The contract check (the owner's explicit question)

`REPORTING_ARCHITECTURE` §12 (failure modes & guarantees):

| Failure | Behavior (the contract) |
|---|---|
| Worker crash | pg-boss retry; **run marked `FAILED`** with correlation id for tracing |
| Storage failure | **Run marked failed**; user told to retry; no "half exports" |

And the codebase's own PHASE-013 precedent (`failRunIsolated`, whose
docstring states the law: the failure record "must SURVIVE the caller's
rollback … the QUEUED row would otherwise never reach FAILED and
pg-boss would retry into the same wall forever") — but that fix
covered only the PRE-execution `FORBIDDEN_AT_RUN` case. **COMPUTE
failures still lost the record**: on the job path the worker's
`withTenant` rollback erased the in-tx FAILED write, leaving the row
QUEUED forever (the exact disease PHASE-013 described); on the inline
path the true error was masked by the 25P02. **So yes — the contract
requires the failure state to be recorded outside the aborted
transaction (for the job path, where a committed QUEUED row exists and
is polled), and requires the true error to reach the caller (both
paths). Fixed accordingly.**

### 2c. The fix (three pieces, the 59085a0 round)

1. **`RunService.executeInline`'s catch (the masking law):** the
   in-tx `failRun` write is attempted (it still serves callers whose
   UoW is alive), but its OWN failure can never replace the compute's
   error — when the UoW is aborted the write is skipped and the
   ORIGINAL error is always rethrown.
2. **The worker's post-rollback recording (the terminal-state law):**
   `recordJobFailureAfterRollback` (run-service, one definition) —
   called by the pg-boss handler's catch in `reporting.module` AFTER
   the worker's UoW rolled back (inside the UoW the isolated write is
   impossible for two distinct reasons: the aborted tx rejects it, and
   a live UoW holds the run row's lock from `markRunning`, so the
   write would block on its own lock until the statement_timeout). It
   records FAILED on an isolated connection via
   **`failRunIsolatedIfActive`** (reporting.store) — CONDITIONAL on
   the row still being `QUEUED`/`RUNNING`, so `FORBIDDEN_AT_RUN`'s
   authoritative record (written pre-lock) and a racing redelivery's
   `SUCCEEDED` are never overwritten. The error still propagates —
   pg-boss retry semantics unchanged.
3. **The inline path's semantics deliberately unchanged:** a failed
   first-run leaves no row (the UoW rolls back whole — nothing
   dangles, no polling surface to strand); the synchronous error
   response is the inline class's "user told" channel; a failed re-run
   leaves the last committed row (the "a re-run replaces its own
   record" law keeps replacement on SUCCESS).

### 2d. The regression pins (each its own run, before → after at the same tree)
