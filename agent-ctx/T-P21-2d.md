## 2. The 7 intent contracts — EXACT payload field lists (2-b builds forms against these)

All ride the FROZEN v2 envelope (`syncCommandSchema`); money = decimal
string ≤ 4dp, qty ≤ 6dp, rate ≤ 8dp (ADR-0009); `?` = optional, `| null` =
nullable. Registry keys in stable order:

1. **`partner:create`** — `partnerCreatePayloadSchema`:
   `kind: "CUSTOMER"|"SUPPLIER"|"BOTH"` (req) · `code?: string(1..40)` (omitted → server auto-numbers `P-NNNNNN`, BR-025) · `name: string(1..200)` (req) · `nameAr?: string(≤200)|null` · `taxNumber?: string(≤200)|null` · `creditLimit?: money|null` · `creditTermsId?: uuid|null` · `priceListId?: uuid|null`.
   NO phone/email/address (contact child rows ride 020's `partner:contact_merge`).
2. **`quotation:create_draft`** — `quotationCreateDraftPayloadSchema`:
   `customerId: uuid` (req) · `quoteDate: ISO date` (req) · `validUntil?: ISO date|null` (omitted → `sales.quote_default_validity_days` default, BR-006) · `note?: string(≤500)|null` · `noteAr?: …|null` · `lines: [{ itemId: uuid; qty; unitPrice?: price(≤6dp, non-neg)|null — null ⇒ server price resolution (BR-003); discountAmount?: money|null; taxCodeId?: uuid|null; description?/descriptionAr?/note?: string(≤500)|null }] (1..200)`.
3. **`delivery_note:create_draft`** — `deliveryNoteCreateDraftPayloadSchema`:
   `customerId: uuid` (req) · `warehouseId: uuid` (req) · `orderId?: uuid|null` (must reference an ISSUED order with the same customer) · `deliveryDate: ISO date` (req) · `note?/noteAr?` · `lines: [{ itemId: uuid; qty; unitPrice?: price|null (null ⇒ item base price); discountAmount?; batchId?: uuid|null; serialIds?: uuid[]|null; description?/note? }] (1..200)`. No orderLineId (offline drafts are standalone/order-header-linked).
4. **`expense:create`** — `expenseCreatePayloadSchema`:
   `categoryId: uuid` (req) · `cashAccountId: uuid` (req — the till/account paid from) · `payeeName: string(1..160)` (req) · `currencyCode: string(3)` (req) · `amount: money` (req, > 0 server-side) · `exchangeRate?: rate|null` · `taxCodeId?: uuid|null` · `receiptFileId?: uuid|null` (stays null offline) · `valueDate: ISO date` (req) · `description?/descriptionAr?`. No partnerId (the owning service consumes none).
5. **`cash_transfer:create_draft`** — `cashTransferCreateDraftPayloadSchema`:
   `fromAccountId: uuid` (req) · `toAccountId: uuid` (req, ≠ from — DDL CHECK) · `currencyCode: string(3)` (req, must match both accounts) · `amount: money` (req, > 0) · `feeAmount?: money` (omitted ⇒ "0.0000"; server rule 0 ≤ F < A) · `exchangeRate?` · `valueDate: ISO date` (req) · `reference?: string(≤200)|null` · `description?/descriptionAr?`.
6. **`stock_transfer:create_draft`** — `stockTransferCreateDraftPayloadSchema`:
   `fromWarehouseId: uuid` (req) · `toWarehouseId: uuid` (req, ≠ from) · `lines: [{ itemId: uuid; qty }] (1..200)` (one line per item — service rule; NO batch at draft: batch binding is FEFO at dispatch) · `note?/noteAr?`. NO date (the owning create takes none — dispatch dates the legs).
7. **`stock_count:submit_lines`** — `stockCountSubmitLinesPayloadSchema`:
   `countId: uuid` (req — an EXISTING session; sessions are created online so the system-qty snapshot freezes server-side) · `lines: [{ itemId: uuid; countedQty: non-neg decimal ≤ 6dp (0 is a legitimate count); batchRef?: uuid|null (disambiguates multi-batch items) }] (1..500)`.

Types exported: `PartnerCreatePayload`, `QuotationCreateDraftPayload`,
`DeliveryNoteCreateDraftPayload`, `ExpenseCreatePayload`,
`CashTransferCreateDraftPayload`, `StockTransferCreateDraftPayload`,
`StockCountSubmitLinesPayload` (all via `z.infer`, all from `@erp/contracts`).

**ACCEPTED result shapes (the confirmation surface):**
- partner: `{ partnerId, code, status }` (+ `entity {id, version}`, feed `partners`)
- quotation: `{ quotationId, status: "DRAFT", totalNet }` (feed `quotations`)
- delivery: `{ deliveryId, status: "DRAFT", totalNet }` (feed `delivery_notes`)
- expense: `{ expenseId, status: "DRAFT", amount }` (feed `expenses`)
- cash transfer: `{ transferId, status: "DRAFT", amount, feeAmount }` (feed `cash_transfers`)
- stock transfer: `{ transferId, status: "DRAFT", lineCount }` (feed `stock_transfers`)
- stock count: `{ countId, status: "DRAFT", lines }` (feed `stock_counts`)
`officialNumber` is **undefined for all seven** — every owning service
assigns numbers at a later lifecycle step (QOT- at send, DEL- at post,
EXP-/TRF- at post, TRN- at dispatch, CNT- at approve); the DRAFT
confirmation is `result` + `entity {id, version}` (asserted in spec #4).

**Audit actions (device provenance — the owning services' own events carry
the actor only):** `partner.offline_created`, `sales.quotation_offline_created`,
`sales.delivery_note_offline_created`, `treasury.expense_offline_created`,
`treasury.cash_transfer_offline_created`, `inventory.stock_transfer_offline_created`,
`inventory.stock_count_lines_offline_submitted` — each with `deviceId` = the
pushing device.

## 4. Decision records (for the completion report)

- **DR-P21-08-2d-1 · quotation OD-create without owner_device_id.** The
  OD pin instruction ("stamp owner_device_id exactly like draft-invoice")
  cannot be executed literally: `quotations` has no `owner_device_id` column
  (0029 granted the substrate stamp to `sales_invoices` ONLY) and 2-d adds
  no migrations (binding boundary). Honest adaptation: (a) the creating
  device is recorded on the `sales.quotation_offline_created` audit row
  (`device_id`); (b) ownership guarding is CREATE-ONLY by registry shape —
  `handlerRegistryKeys()` carries no `quotation:update_draft`, so ANY
  device's update attempt (owner or not) is an unknown-intent rejection
  (spec #7 asserts both the registry absence and the rejection with
  `details.supported`). A future update intent would need its own DR +
  migration.
- **DR-P21-08-2d-2 · rejection-reason mappings (no new wire reasons).** The
  owning services' typed error codes are NOT in SYNC_REJECTION_REASONS, so
  `rejectFromSyncError`'s existing fallback surfaces them as
  `VALIDATION_ERROR` with the service's typed message intact. No
  catch-and-remap layer was added (that would be a second business-logic
  path; the raw-propagation pattern is what pos-sale/draft-invoice do).
  Mappings exercised in specs:
  | Intent | Service rule | Typed code | Wire reason |
  |---|---|---|---|
  | partner:create | unknown price list | PRICE_LIST_NOT_FOUND | VALIDATION_ERROR |
  | quotation:create_draft | INACTIVE customer | SALES_DOCUMENT_STATE | VALIDATION_ERROR |
  | delivery_note:create_draft | SERVICE item | DELIVERY_LINE_INVALID | VALIDATION_ERROR |
  | expense:create | negative amount | INVALID_AMOUNT | VALIDATION_ERROR |
  | cash_transfer | fee ≥ amount | TREASURY_DOCUMENT_STATE_INVALID | VALIDATION_ERROR |
  | stock_transfer | same warehouse | STOCK_TRANSFER_SAME_WAREHOUSE | VALIDATION_ERROR |
  | stock_count | non-DRAFT session | STOCK_COUNT_STATE_INVALID | VALIDATION_ERROR |
  (ITEM_INACTIVE — registry-native — remains available to these intents via
  `requireSellableItem`, untouched.)
- **DR-P21-08-2d-3 · stock_count:submit_lines maps to `enterCounts`, not
  session submit.** SD-aggregate honors the matrix row "stock count lines":
  the handler resolves every `(itemId, batchRef)` payload line to the
  session's lineNo BEFORE any write (unresolvable/ambiguous/duplicate →
  typed VALIDATION_ERROR, zero residue) and applies the batch through
  `CountService.enterCounts` (the blind-safe line-entry path). Session
  submit/review/approve (variance + G-13/G-14 posting) stay online server
  decisions.
- **DR-P21-08-2d-4 · feed entries for non-group entities.** All 7 handlers
  declare header-only `{id, version}` UPSERT feed entries in the same tx
  (change_log `ck_change_log_entity_shape` accepts all the names). Only
  `partners` is in a pullable feed group today; the other six types'
  change_log rows are future substrate — pull rejects them
  (`SYNC_ENTITY_NOT_PULLED`, spec #23) per the frozen 020 scope
  (desktop = POS group + sales_invoices); the device's confirmation rides
  the push result.
- **DR-P21-08-2d-5 · service API adaptations** (schema mirrors the REAL
  service inputs, not the task's field sketches — recorded where they
  differ): partner create has no phone/email/address (child-table surface =
  contact_merge); expense has no partnerId; delivery needs
  customerId+warehouseId (both NOT NULL server-side); stock transfer has no
  batchRef/date at draft; quotation uses `customerId`/`quoteDate` (the
  service's own vocabulary, consistent with the 020 draft-invoice schema).
- **Idempotent replay posture (verified):** the push service's inbox dedupe
  (commandId+idempotencyKey) runs BEFORE handler lookup — handlers never
  see replays; none of the seven draft paths posts journals, so no INV-013
  surface exists on them. C-01 asserted per intent (duplicate:true ACCEPTED
  + target-table count unchanged).

## 6. Deviations / notes for the completion report

- The 3 existing PushService construction sites were mechanically extended
  (required by the additive constructor; no assertions changed — the full
  020 sync suite passes bit-identically, 103/103).
- Spec fixture uses a dedicated tenant `2d2d2d2d-…` + 8 desktop devices
  (one per intent cluster + the OD second device) because the push rate
  bucket is PER DEVICE (burst 20 / refill 10-min) — a single device across
  26 pushes hits DEFERRED (hit during development; the pool keeps each
  cluster ≤ 4 pushes). Devices are created directly (the policies.spec
  pattern — preferred over the enroll endpoint for spec bootstrap).

  (pg returns `count(*)` as a string; the wire result is JSON-typed).

  (partner-create desktop column etc.) flip implemented:true in WAVE 4 —
  untouched here; this spec (`sync/desktop-intents.spec`) is the gate name
  to cite.
