## Deviations (numbered — payload shape adjustments discovered from the real services)

1. **The credit-note payload mirrors `CreditNoteService.create`'s REAL input,
   not the brief's loose sketch** (the brief's own instruction — "mirror the
   sales credit-note draft shape" — wins): `invoiceId` is REQUIRED and must
   reference a POSTED invoice (BR-004 — the reference is never optional);
   lines are keyed by `invoiceLineId` (the item, the original price, the tax
   snapshot and the W-3 issue-cost re-entry value are all derived server-side
   from the invoice line — never trusted from the device); `returnToStock` is
   the per-line stock-re-entry flag; the customer is derived from the invoice
   (no `partnerId` in the payload); the brief's `reason` field maps to the
   line/header `note`/`noteAr` fields.
2. **`repAttribution` has no column home — attribution rides `created_by`**
   (deviation recorded in the handler header): receipts carry no sales-rep
   column (0012 DDL; a new column would be a migration — out of the reuse-first
   scope). The field rep IS the device user: `created_by = ctx.userId` + the
   device-stamped audit event (`treasury.receipt_field_collection_posted`)
   are the attribution surface — exactly how the 017 rep-day settlement ties
   a collection (`repDayCollections` by the rep cash account + value date).
   The payload keeps `collectedAt` as an advisory capture moment (never
   trusted; `valueDate` is the server-final business date).
3. **The registry grows 13 → 17 keys, not 13 → 16**: the plan's "13 → 16"
   counts the van pair as ONE intent — the registry actually carries FOUR new
   keys (`receipt:create_field_collection`, `van:confirm_load`,
   `van:confirm_unload`, `credit_note:create_draft`; the van pair is two
   intents, two handlers, one capability row #12). Asserted in test 18 with
   the reasoning comment.
4. **`PARTNER_INACTIVE` has no module error class** — the handler throws
   `DomainError("PARTNER_INACTIVE", …)` directly (the draft-invoice
   `FORBIDDEN` precedent). `ReceiptService.create` checks partner EXISTENCE
   only, so the ACTIVE-status gate is the handler's typed pre-write seam (the
   021 deactivated-master-data vocabulary rule: the actionable reason, never
   a generic VALIDATION_ERROR).
5. **The double-load mapping splits by state** (the brief allowed
   "STALE_VERSION or VALIDATION_ERROR with details"): an already-POSTED
   transfer (a genuine double-confirm — the row's state changed underfoot
   since the device snapshotted it) → `STALE_VERSION` with
   `{transferId, currentStatus}`; a DRAFT transfer (the load has not left the
   warehouse yet — a premature confirm) → `VALIDATION_ERROR` with the same
   details shape. The underlying `StockTransferStateError`
   (`STOCK_TRANSFER_STATE_INVALID`) is not a wire reason — the pre-gates keep
   the common cases off the honest-fallback path.
6. **The unload's mirror refresh is handler-side**: `VanStockService.unload`
   creates + dispatches but does not refresh the van mirror (only
   `receiveTransfer` does — the 017 board contract gap). The handler performs
   the mirror-first read (`listVanStock` — refresh + read, the
   pull-fields.spec precedent) both for the INSUFFICIENT_STOCK pre-check and
   once more after the service call, so the van snapshot and the `van_stocks`
   feed reflect the return in the SAME transaction. The 017 service file is
   untouched (reuse-first).
7. **No `uomId` on the van payload lines** — the real service lines consume
   `{itemId, qty}` only (the item's base unit; batches/slices resolve
   server-side at dispatch). The 021 rule "accepts EXACTLY what the owning
   service consumes" wins over the brief's sketch; a wire field the server
   ignores would be noise.
8. **The posted receipt reads version 2** (`insertReceipt` starts at 1; the
   POST status flip bumps it) — the spec pins version 2 (the pos-sale pattern
   reads the row's CURRENT version after the chain).
9. **Four `PushService` constructions updated** (`_oracle.makeSyncServices`,
   `push.spec.ts`, `policies.spec.ts`, `desktop-intents.spec.ts`): the
   additive-slot precedent — 021 updated the 020 specs' constructions the
   same way when it added its seven slots. 14 added lines each; no behavior
   change (all four suites re-verified green in the full sweep).
