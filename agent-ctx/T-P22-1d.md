## Binding mechanics applied (MASTER-PLAN §6 + DR-P22-05/05a)

- **Feed groups (golden constants §0, byte-exact):**
  `FEED_GROUPS.field` = the POS base (`items`, `barcodes`, `uoms`,
  `price_list_items`, `partners`, `tax_codes`, `pos_terminals`,
  `cashier_shifts`) + **`van_stocks`, `routes`, `settlement_templates`,
  `statements`**; `FEED_GROUPS.personal` = **`statements`, `sales_invoices`,
  `receipts`, `notifications`**. `PULLED_ENTITY_TYPES` is the deduped flat
  union (the contracts subset proof holds). The pull gate
  (`isEntityPullableByDevice`) serves `SYNC_ENTITY_NOT_PULLED` outside the
  group — proven for field (receipts/notifications/desktop-class/no-device
  paths) and personal (items/van_stocks/routes/settlement_templates).
- **Entity naming (the wire vocabulary):** `van_stocks` = the PHASE-017
  mirror table of the same name; `routes` = route headers + their ordered
  `route_customers` list riding the row as `customers[]`;
  `settlement_templates` = the PHASE-017 `rep_settlements` header read model
  (the 022 mobile cache's NAME — source table differs, entity type is the
  field app's); `statements` = per-partner snapshots computed at pull time
  over the REAL AR subledger via `ArQueriesService.statement` (BR-028 — no
  second source of truth; the `permissions`-snapshot pattern: content-diff
  catch-up, `version` null on the wire, change row `id` IS the partner id);
  `receipts`/`notifications` = the 0012/0021 tables.
- **Pull wiring is GENUINE end-to-end (not just declared):** `routes`/
  `settlement_templates`/`receipts`/`notifications` ride the generic
  watermark catch-up (`projectSource` cases + `syncFeed`), all proven by
  payload assertions over REAL service chains (registerVan → loadOut →
  receiveTransfer → unload for van_stocks; create→submit→approve→post for
  the statement content; the REAL distribution services for routes +
  settlement). `van_stocks` rides the dedicated catch-up because the 017
  mirror is rebuilt by delete+insert: UPSERTs for the touched slice + the
  vanished-key DELETE diff (`op:'DELETE'`, `payload:null`, a `tombstones`
  row) — idempotent, proven including the quiet-tenant no-op re-pull.
- **Personal scope (LOCAL_DATABASE §1.1 rule 2, server-side):** the
  android-personal serve filter `personalServeScope` rides the change_log
  serve query itself: `sales_invoices` → `payload->>'customerId' =
  linked_partner_id`, `receipts` → `payload->>'partnerId'`, `notifications`
  → `payload->>'userId' = device user`; **an unlinked personal device AND any
  personal-group entity without a scope key fail closed (`AND false`)** —
  never an unscoped serve. `statements` scope via the dedicated feed's
  partner set (linked partner ONLY). Proven with fabricated other-partner
  ledger content + stolen/forged/cross-entity cursors (asserted never widen
  the scope) + the NULL-user broadcast never served.
- **Migration 0033 (DR-P22-05a):** one nullable column
  `devices.linked_partner_id` — the personal device's linked partner. devices
  stays service-mediated (PHASE-003 §4: no tenant_id, no RLS), so a
  cross-plane FK into the RLS'd partners table is impossible by design; the
  column is validated by the registration surface (2-b's) and consumed by the
  pull path. NULL = no linkage → empty partner scope (fail closed). No
  business-schema change, no data change, no RLS change; schema_version 33.
  The production writer of the column is task 2-b's registration surface;
  the specs seed it directly (the desktop-intents precedent).
- **Budgets:** the server keeps enforcing the existing ≤ 2 MB delta page cap
  (proven for the new entities — the two ~1.1 MB notification rows split
  pages, first item always rides); the 256 KB personal background budget is
  CLIENT-side (transport, task 2-a) per MASTER-PLAN §6 ("document which side
  enforces what" — recorded here and in the pull-service header).

## Deviations / recorded observations

1. **Final entity-type names (the wire vocabulary, recorded for the phase

   MASTER-PLAN §0 golden constants byte-exactly. No rename needed.
2. **Migration decision (DR-P22-05a, verbatim commitment):** ONE minimal
