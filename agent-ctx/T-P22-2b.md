## Binding mechanics applied (MASTER-PLAN §7 / DR-P22-09)

1. **Keystore rules (SECURITY_AND_DEVICE_MANAGEMENT §3, the table quoted in
   secure-store-port.ts):** access token MEMORY ONLY (MobileSession; the
   SECRET-SCAN test proves no token material reaches ANY store table);
   refresh token + device keypair + (device-owned) SQLCipher dbKey in
   SecureStorePort under `erp.<deviceId>.*`; the enrollment writes the
   vault ALL-OR-NOTHING (a failed hop persists nothing — the desktop
   invariant, proven by the attest-rejection test). The enroll-time access
   token rides the RESULT to `MobileSession.prime()` and dies with the
   process.
2. **Rotation + reuse detection (ADR-0015 §3 / M-05):** the exchange is the
   PUBLIC POST /:id/refresh (credential-in-body — no Authorization header,
   the login pattern); the successor is persisted BEFORE the call resolves
   (the desktop session contract); presenting a rotated/consumed token is
   answered 401 DEVICE_REFRESH_INVALID (error.filter.ts's device mapping,
   verified) → `wipeDeviceCredentials` + `ReLoginRequiredError
   (REUSE_DETECTED)`; 403 DEVICE_REVOKED → the same wipe under the
   kill-switch reason; the session's `onRotationFailure` (ROTATION_FAILED /
   NO_CREDENTIAL) is the D-01 hook — proven end-to-end (session presenting
   a stale copy → typed error + hook + cleared memory + wiped vault).
   NON-credential failures (404, network) propagate WITHOUT a wipe — a
   transient network blip must not destroy the vault (Deviation 5).
3. **The enrollment journey (DR-P21-01 adapted):** register under the
   LOGGED-IN identity (`registerAuthorization` — the customer-portal
   identity for the personal class per the brief) with platform "android",
   the class from MOBILE_DEVICE_CLASSES, capabilities from the new labels,
   appVersion + SYNC_CONTRACT_VERSION + the CryptoPort public key → the
   server-issued nonce is signed with REAL Ed25519 (the fake server in the
   suite verifies it with node:crypto against the registered key — the
   verifier is never mocked) → the one-time enrollmentSecret exchange
   (forwarded EXACTLY once, single-use proven: a replay answers the typed
   401) → the vault. The returned contractVersion is the C-08 gate input.
4. **Trust degradation (D-07 / SECURITY §7):** best-effort signals →
   `{trustFlags}` on the registry's PATCH surface (the exact patchSchema
   body); flagged → `trustPolicy` = "online-only" until the admin ack
   (`adminAckedAt` read from the sync status's device.trustFlags); the ack
   covers ONE episode — a detection observed AFTER the ack re-flags;
   `onlineWriteGate`: normal queues locally, flagged+online = live-write
   only (caching disabled), flagged+offline = the write refused with an
   honest reason — reads/the gate/every non-write surface stay up (degrade,
   never brick; the report itself is best-effort — a 403/network failure is
   an honest `{reported:false}` outcome that never blocks registration).
5. **The 7-day watermark (D-04 / SECURITY §5.3):** `permissionWatermarkState`
   over meta `permissionSnapshotAt` (the sync-core watermark key — ISO /
   epoch-ms / numeric-string accepted, junk → NO_SNAPSHOT fail-closed);
   ≤ 7 days fresh (exactly 7 days still fresh — the `ageDays > 7` boundary),
   7 d + 1 s → stale → `offlineWritePolicy` = read-only +
   online-required-for-writes (no local queueing; a write WITH connectivity
   goes through the live path) + the as-of label for the honest-state
   banner. The snapshot gates UI ONLY — server enforcement is final (§5.2;
   sync-core's assertWritable stays the engine backstop).
6. **D-01 revoke flow (§6.2):** `handleDeviceRevocation` — session clear
   FIRST (stop presenting the dead credential), purge via 2-a's
   `purgeOnRevocation` (outbox included; per-profile table lists; honest
   per-table report), vault wipe, and the re-login UX state
   (`requiresReLogin: true`); `deviceRevocationHandler` is the
   `MobileSyncHostOptions.onRevocation` wiring shape (2-a's
   RevocationDetection payload).

## Deviations (numbered)

1. **2-a's `sync/http-port.ts` method union widened `"GET" | "POST"` →
   `"GET" | "POST" | "PATCH"`** — the devices registry's trust-flag surface
   is `PATCH /api/v1/devices/:id` (devices.controller.ts row 4), and the
   brief's `reportTrustSignals(httpPort, …)` runs over 2-a's seam. Additive
   only (the sync transport keeps GET/POST; implementations forward the
   string to fetch); the header documents the T2-b widening; the full 2-a
   suite re-verified green.
2. **The personal-class partner link: CARRIED client-side, not yet
   server-consumed (the honest server reality).** The brief said "the
   register call for personal devices carries/receives the partner link
   (1-d added linked_partner_id)". Verified against the server: migration
   0033 added `devices.linked_partner_id`, but the registerSchema (zod,
   non-strict) has NO such key — it STRIPS unknown fields, and NO production
   route writes the column (the pull specs seed it directly; 1-d's note
   "the production writer of the column is task 2-b's" presumed an API-side
   change that 2-b cannot make with apps/api read-only). The mobile client
   therefore: REQUIRES `linkedPartnerId` for android-personal (fail-loud
   before any HTTP call — an unlinked personal device pulls an empty partner
   scope by design, so refusing at enroll time is the honest posture) and
   CARRIES it on the register body for the surface when it lands. The test
   asserts the carried shape. Handed off (below).
3. **The trust-signal PATCH route is `identity.devices.manage`-guarded (the
   admin plane)** — a plain field device's self-report under its own access
   token is answered 403 by the current server build. The device-side report
   is BEST-EFFORT by design (D-07): every failure class is an honest
   `{reported: false, …}` outcome that never blocks registration or syncing
   (proven). A server-side self-report widening (the revoke/push-token
   `self: true` pattern) is a server decision, out of 2-b's read-only scope —
   recorded for the phase report.
4. **Attestation is not optional in the mobile flow** (the desktop's
   enrollDesktopDevice had an optional attest closure): the mobile client
   ALWAYS presents a deviceKeyPublic, so the server ALWAYS issues a nonce
   and the attest hop always runs with a REAL signature. A server that
   issues no nonce (attestationNonce null) skips the hop — the code path
   exists and is documented (kept for forward compatibility).
5. **The wipe-on-failure classification is narrower than the desktop's at
   the exchange level (intentional refinement):** the DESKTOP session
   cleared its memory token on ANY exchange failure; the mobile port keeps
   exactly that at the session level (clear + onRotationFailure on any
   throw), but `rotateDeviceRefreshToken` only wipes the VAULT on the
   credential-terminal classes (401 DEVICE_REFRESH_INVALID / 403
   DEVICE_REVOKED). A network blip or a 404 must not destroy a possibly
   still-valid refresh token (the next trigger retries) — proven by the
   404-keeps-the-token test. Reuse still wipes unconditionally (the theft
   signal is terminal by definition).
6. **`NodeCryptoDriver` lives in `src/auth/crypto-port.ts` (node:crypto in
   src)** — the 2-a `src/store/node-driver.ts` precedent (better-sqlite3 in
   src; the device driver lives in native/). Verified: mobile typecheck
   green (node:crypto resolves, like the desktop's minisign.ts).
7. **A fifth test file** (`device-registration.test.ts`) beyond the brief's
   four — the orchestrator + the D-01 revoke-flow client got their own file
   over the REAL stores; auth.test.ts stays 1:1 with the brief's listed
   shapes.
8. **MobileSession gained `msUntilDue()`** (the "silent refresh scheduling
   hook" the brief asked for): the ms until the next silent refresh should
   fire (null when no token is held) — the native App arms a timer against
   it (`setTimeout(() => void session.silentRefreshIfDue(), …)`); the timer
   itself stays outside the class so tests stay sync. The desktop had no
   equivalent (its shell polled).
