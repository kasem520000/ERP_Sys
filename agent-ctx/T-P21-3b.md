## DR-P21-3b-1 — the E2E-exposed 2-b enqueue defect (the headline finding)

**Symptom (observed live):** after reconnect + SyncNow, the console's
queued command is pushed but the row freezes `IN_FLIGHT` forever — the
mirror renders "syncing" indefinitely, no rejection can ever render, no
draft can ever sync.

**Root cause (one column, two consumers, two incompatible semantics):**
`apps/web` `store-client.enqueueDraftCommand` writes the BUSINESS PAYLOAD
into the outbox `payload` column (`JSON.stringify(command.payload)` —
pinned by its own unit test, store-client.test.ts:101), but the engine's
wire reconstruction (`SyncClient.pushAllV2` → `transport.pushV2`) sends
`JSON.parse(row.payload)` VERBATIM as the wire command. The pushed command
carries NO `commandId/entityType/intent/idempotencyKey` (wire evidence:
`[["customerId","orderDate","lines"]]`), so the per-item result cannot be
attributed (`applyResultsV2` matches by `result.commandId` → `byId.get` →
undefined → skipped). Verified against the REAL server shape too:
`push-service.normalize()` shape-rejects the bare payload (VALIDATION_ERROR
with `bestEffortId` = a RANDOM UUIDv7 — same unattributable freeze). The
engine's own enqueue contract stores the FULL ENVELOPE
(`ReferenceDevice.capture`: `payload: command`) — 2-b's "the row the
shell-side drain picks up" claim in its completion record is falsified by
this seam, which no 2-b unit test crossed (the console never drains; the
engine's tests never enqueue through the console).

**The fix — VERIFIED END-TO-END in a local trial, then REVERTED (out of my
lane; apps/web is untouchable per the task boundary).** The trial applied
exactly this and BOTH journeys went fully green (8.6 s, AR + EN, zero spec
changes — the spec's payload assertions read both sanctioned shapes):

1. `apps/web/lib/shell/store-client.ts` (enqueueDraftCommand):
   `JSON.stringify(command.payload ?? null)` → `JSON.stringify(command)`
   (the full v2 envelope — the wire command).
2. `apps/web/components/offline/outbox-view.tsx` (`parseRowPayload`): a
   compatibility unwrap — when the parsed object is a v2 envelope
   (`entityType` + `intent` + object `.payload`), return `.payload`;
   bare business payloads (older rows) pass through unchanged. This keeps
   accept-server-price/accept-partial working (they need `payload.lines`).
3. `apps/web/lib/shell/__tests__/store-client.test.ts:101` (the ONE test
   pin): `expect(outbox.payload).toBe(JSON.stringify(command.payload))` →
   `JSON.stringify(command)`.
   Trial result: `pnpm --filter @erp/web test` = 72/73 (exactly this pin
   red); every other 2-b test green (the compat unwrap preserves the
   component-suite fixtures). Optional cosmetic: `console.tsx` choose() can
   unwrap the envelope for the `local_events` payload column (the journey
   asserts `toContain(serverPrice)` which passes either way).
   Alternative sanctioned shape (if the coordinator prefers): keep the
   payload column as the business payload and rebuild the envelope at the
   HOST transport seam (apps/desktop `ObservingTransport.pushV2`) from the
   outbox row columns — the spec tolerates both.

## Honest finding #2 — the §3 trace-id audit gap (for W4, minor)

`parseTypedRejection` reads `traceId` from the TOP LEVEL of the typed
lastError JSON, but sync-core's typed JSON is `{reason, resubmittable,
details, message}` — no top-level traceId (the real server's push results
carry none either; handlers may put one in `details`). Consequence: the
`local_events.trace_id` audit column logs NULL and the "trace: …" line
does not render, even though the trace id IS in the server message +
details block (rendered). Phase acceptance criterion 5 ("every user choice
audit-logged with the rejecting response's traceId") is therefore only
partially met on the console surface. Cheap fix options (2-b's console):
read `details.traceId` as a fallback in `parseTypedRejection`; the
harness transport already models that shape.
